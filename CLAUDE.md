@AGENTS.md

## Working directory

The shell already starts at the repo root. Never `cd` in shell commands — not into subfolders, the scratchpad, `/tmp`, or `node_modules`, and not back to the repo root either. Run everything with repo-relative paths (`npx tsc --noEmit`, `grep -r foo components/`).

## What this is

Letterboxd for DJ sets, and a community-built database of the electronic music scene. Users log a night out (event, venue, date, day/night, lineup), rate and review the night and/or each DJ, tag the crowd and their friends, and follow each other for a feed with likes, comments and push notifications. Those logs are also the database: every DJ, venue and event gets a page that collects its reviews, ratings and stats (who people saw where, how it rated). There's no editorial layer — all of it comes from what users log, so features that improve logging quality (deduping DJs/venues/events, Google Places venues, Spotify DJs) matter for the data, not just the UX.

Stack: Expo (React Native + React Native Web) with Expo Router, NativeWind for styling; a Go HTTP API deployed on AWS (ECS Fargate previously, currently a single EC2 instance running Docker Compose for cost reasons — see `infra/terraform/README.md`); AWS RDS Postgres; Clerk for auth. The web export still deploys via Vercel (static hosting only — the API used to live there too as tRPC Edge Functions, but moved off after an unfixable Vercel Edge Function bundler bug; see git history around the "move to aws and go backend" commit for the full story).

## Commands

Setup:
```
npm install
cp .env.example .env   # fill in EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY, EXPO_PUBLIC_API_URL
cd server && cp .env.example .env   # fill in DATABASE_URL, CLERK_*, SPOTIFY_*, GOOGLE_PLACES_API_KEY and EXPO_ACCESS_TOKEN (both optional) — see server/.env.example
```

Running locally — the app talks to the API over HTTP, so both need to be up:
```
npm run dev             # macOS: scripts/dev-windows.sh — docker compose up -d, migrate, seed, then opens dev:app and the API logs in separate Terminal.app windows
npm run dev:concurrent  # runs dev:api and dev:app together in one terminal via concurrently
npm run dev:api         # docker compose up for server/ (Postgres + Go API), API on :8080
npm run dev:app         # expo start — press w for web, i for iOS simulator
```

First-time local DB setup (against the docker-compose Postgres, entirely separate from the production RDS instance):
```
npm run db:migrate   # applies server/migrations/*.sql via golang-migrate
npm run db:seed      # fixture data (2 users, a handful of DJs, an Innervisions day party + night, reviews/tags/likes/comments)
npm run db:reset     # migrate down, up, and re-seed
```

Type checking: `npx tsc --noEmit` (client). Server: `cd server && go build ./... && go vet ./... && go test ./...` (there is no lint script or unit test runner configured for the client).

End-to-end: `npm run test:e2e` (Playwright, `e2e/`, desktop + phone viewports of the web build, signed out). It starts its own API on :8090 against a fresh `beatboxd_e2e` database in the compose Postgres (recreated, migrated and seeded each run by `scripts/e2e-api.sh` — your dev `beatboxd` DB is untouched) and its own Metro on :8091 (`EXPO_PUBLIC_DEV_API_PORT` points the dev client at the e2e API). Needs Docker and Go; first time, `npx playwright install chromium`. Tests assert on seed fixtures, so keep `server/cmd/seed/main.go` and the specs in sync.

## Architecture

**Routing**: `app/` is Expo Router file-based routing. `(auth)` and `(tabs)` are route groups; `app/_layout.tsx` is the root layout and wraps everything in `ClerkProvider` → `QueryClientProvider`. All in-app links and navigation must go through the `ROUTES` constant in `lib/routes.ts` — never hardcode a path string in `Link href`, `router.push`/`replace`, or `Redirect href`. Static routes are plain `Href` values (`ROUTES.FEED`, `ROUTES.SIGN_IN`); dynamic routes are functions that build the `Href` from an id/slug (`ROUTES.DJ(slug)`, `ROUTES.USER(username)`). When a new route is added under `app/`, add a corresponding entry to `ROUTES` in the same change.

**Components & page layout**: generic, domain-agnostic UI primitives (`Text`, `Card`, `GlassSurface`, `Button`, `Avatar`, `RatingStars`, `EmptyState`, `Page`, `PageHeader`, …) live in `components/ui/` and are imported from its barrel (`components/ui`). Components that know about reviews/DJs/users (`ReviewCard`, `StatsSummary`, `FavoritesShowcase`, …) stay in `components/` — but only once they're used from two or more files. A component used by a single file lives in that file as an unexported function (Expo Router turns every file under `app/` into a route, so a screen's helper components can't sit beside it as separate files); promote it to `components/` when a second consumer appears. When pulling in a [React Native Reusables](https://reactnativereusables.com) component, adapt it straight into a single `components/ui/` file built on its `@rn-primitives/*` package with the app's API and theme (as `ui/Avatar` does) — don't keep a separate raw copy plus a wrapper. If a component needs RNR's `cn` helper, use `tailwind-merge` v2 (v3 requires Tailwind 4). Every screen renders inside `<Page>` (safe area + the concrete-wall background, optional `title`/`channel`/`header`, `fullBleed` for a hero that runs under the status bar), and lists/scroll views take `usePageContentStyle()` as their `contentContainerStyle` so content lines up with the shared horizontal gutter (`components/ui/layout.ts`) — don't hand-roll `SafeAreaView` or `padding: 16` on a screen. Custom top-of-screen blocks (profile/detail headers) go in `<PageHeader>` (with `border="primary" | "accent"` for the divider) to stay on the same gutter. The look is a dark-only "zine" (the app forces the dark color scheme in `app/_layout.tsx`): colored paper `Card`s (`tint` purple/red/near-black panel, optional `tilt`/`torn`), `RatingStamp` seals instead of stars for showing ratings, `Chip` tags, and Jersey 10 uppercase for headings and labels.

**API**: the Go service in `server/` (see `server/README` references in `infra/terraform/README.md` for deploy details). Handlers live in `server/internal/httpapi/`, one file per domain (`djs`, `events`, `logs` (the one-shot "log a night" endpoint), `venues`, `tags`, `follows`, `reviews` (incl. likes/comments), `favorites`, `users`, `feed`, `push_tokens`, `app_version`, plus `webhooks` for the Clerk sync endpoint), wired up in `server/internal/httpapi/router.go`. Business logic that doesn't belong in a handler (feed ranking/interleave, tag normalization, Spotify, Google Places and Expo push clients, slugify) lives in `server/internal/domain/`; DB access is hand-written SQL in `server/internal/db/queries/` against `pgx`/`pgxpool` (no ORM). This is a plain REST API (no tRPC), but it's not undocumented either: every handler carries `swag`-style `@Summary`/`@Param`/`@Success`/`@Router` doc comments, and `server/docs/{swagger.json,swagger.yaml}` (generated, not hand-written — run `make openapi` in `server/` after touching a handler's signature or docs) is served live at `/docs/*`. Response types on the client are generated from that spec too — see "Client data fetching" below — so a handler's real output shape and the client's compile-time types can't silently drift the way they could with plain hand-written types.

**Auth flow** (`server/internal/httpapi/middleware.go` + `server/internal/auth/clerk.go`): the client attaches a Clerk-issued bearer JWT on every request (`lib/api/client.ts`'s `useApi()`, via `getToken()` from `@clerk/expo`). The Go service verifies that JWT itself against Clerk's public JWKS (no Clerk SDK needed for this). `RequireAuth` then resolves the verified Clerk ID to a row in the local `users` table — and **lazily creates one with a fallback username if it doesn't exist yet**, in case the Clerk webhook hasn't landed. The webhook handler (`server/internal/httpapi/webhooks_handlers.go`, svix-verified) is the primary sync path for `user.created`/`user.updated`/`user.deleted`; the lazy-create in `RequireAuth` is just a race-condition fallback, not the main path — don't remove one without considering the other. On the client, `AuthProvider` (`lib/auth.tsx`, mounted in `app/_layout.tsx`) owns the single `/users/me` query; read the current user anywhere with `useCurrentUser()` (`{ me, isSignedIn, isLoaded, isLoadingMe }`) instead of writing another `useQuery` for it. After a profile update, `setQueryData(queryKeys.users.me(), updated)` still works — it updates the provider's query. Sign out with `useSignOut()` from `lib/push.ts`, never Clerk's `useAuth().signOut` directly: it unregisters the device's push token first, so the old account's notifications stop arriving on that device.

**Data model** (`server/migrations/*.sql`, plain Postgres DDL applied via `golang-migrate`): `users`, `djs`, `venues`, `events`, `logs`, `log_lineup`, `reviews`, `review_likes`, `review_comments`, `review_tags`, `tags`, `review_tag_links`, `favorite_reviews`, `follows`, `push_tokens`. An `events` row is just a named party ("Innervisions NY", unique by `lower(name)` and `slug`) — not a night: it happens at any number of venues and dates and collects every log of it, and its page (`/event/<slug>`) rolls them up. A `logs` row is one person's night out: an optional `event_id` (null = a one-off night with no event name, just the venue), the venue (`venue_id`, with `venue` keeping the display name denormalized), `seen_at` (the day), `is_day`/`is_night` (when *this person* went — at least one set, both = day into night), and the DJs they saw in `log_lineup`. Day/night and date live on the log, never the event: people at the same event can go during the day or at night, or on different dates, and there are no shared per-night records to merge them into. `reviews` is the core entity — one rating of one DJ, or (with `dj_id` null) of the night as a whole — and always belongs to a log (`log_id`); `rating` is whole stars, an integer 1–5 (no half stars), and `reviews.seen_at` is a copy of its log's, kept for the feed/profile pagination that orders on it. `POST /api/logs` is the only way to create logs and reviews: it takes `eventId` (picked from `GET /api/events?q=`) or `eventName` (found or created by name), the venue, date and day/night, the lineup, and the night and DJ reviews, and saves them in one transaction; deleting a log's last review deletes the log. Logs point at a `venues` row via `venue_id`; a venue is either linked to a Google Places place (`google_place_id`, unique; looked up via `GET /api/venues/places-search` and saved on first use) or typed in by hand (unique by `lower(name)`). Two different "tag" concepts — don't mix them up: `tags` + `review_tag_links` are free-form descriptive tags on a review ("packed", "groovy"; a shared library with some `is_default` seeds, names normalized by `domain.NormalizeTag`), while `review_tags` tags *users* (friends you went with) on a review. `follows` has no surrogate key, just a composite PK on `(follower_id, following_id)`. `push_tokens` keys on the Expo push token itself, so a device that signs in to another account moves to it. Schema changes: hand-write a new numbered `.up.sql`/`.down.sql` pair in `server/migrations/` (there's no schema-diffing tool), and remember production needs the migration applied before or alongside the deploy that uses it.

**Client data fetching**: `lib/api/client.ts`'s `useApi()` hook returns a small `{get, post, patch, del}` client bound to the current Clerk token, pointed at `EXPO_PUBLIC_API_URL` in production builds; in `__DEV__` it instead auto-targets `:8080` on the host serving the Metro bundle (page hostname on web, `Constants.expoConfig.hostUri` on native), so LAN IP changes need no `.env` edit. Each screen calls it directly with `@tanstack/react-query`'s `useQuery`/`useMutation`/`useInfiniteQuery`, using the key factories in `lib/api/queryKeys.ts` (no tRPC — keys are hand-assigned, not auto-derived). A query or mutation used by two or more screens gets a shared hook in `lib/api/hooks.ts` (e.g. `useUserReviews`, `useDjSearch`; current-user reads/writes live in `lib/auth.tsx` as `useCurrentUser`/`useUpdateProfile`) so the key, params and cache writes stay consistent; single-screen queries stay inline in that screen. Response types in `lib/api/types.ts` are aliased from `lib/api/generated.ts`, which is **generated, not hand-written** — `npm run codegen:api-types` regenerates `server/docs/swagger.json` from the Go handlers' doc comments (via `swag`) and then `lib/api/generated.ts` from that spec (via `swagger2openapi` + `openapi-typescript`; see `scripts/generate-api-types.sh`). Request body types in `lib/api/types.ts` stay hand-written (lower drift risk, and OpenAPI's json-schema shapes don't cleanly express TS's optional-vs-omitted distinction that `taggedUserIds` relies on). `.github/workflows/server-ci.yml` regenerates both the spec and the TS types on every PR touching `server/**` or `lib/api/**` and fails the build if either drifted from what's committed — so run `npm run codegen:api-types` and commit the result whenever a handler's shape changes. One known imprecision: Go doesn't distinguish "field always present, sometimes null" from "field always present, never null" in a way `swag` picks up, so nullable fields (e.g. `Dj.bio`) type as non-null in the generated types even though they can be `null` at runtime — every current call site already guards these with truthy checks regardless, but don't chain off one of these fields without a null check just because TS doesn't complain. Dates arrive as RFC3339 strings, not `Date` objects (screens already wrap them in `new Date(...)` where displayed).

**Push notifications**: follows, new likes and comments on someone's review trigger an Expo push (`server/internal/httpapi/notify.go`). They're sent in a goroutine after the request's own work succeeds, on a fresh context, and failures are only logged — never fail the triggering request on them. `queries.Follow`/`LikeReview` report whether a row was actually inserted so repeat follow/like toggles don't re-notify, and self-likes/comments are skipped. Tokens Expo reports as `DeviceNotRegistered` are deleted. The payload's `data` says what happened (`{type: "follow", username}` / `{type: "like" | "comment", reviewId}`), never a path; the client maps it to `ROUTES` in `lib/push.ts`, which also registers the device (asking permission on first signed-in launch) and handles taps, including the one that cold-starts the app. `lib/push.web.ts` is a no-op stub (no web push). Push needs a dev/production build on a real device (not Expo Go on Android, not simulators) and APNs/FCM credentials in EAS; `EXPO_ACCESS_TOKEN` is only needed if the Expo project has enhanced push security on.

**Deployment**: Vercel builds the Expo web export (`expo export -p web`, see `vercel.json`) into `dist/` — no `/api/*` on Vercel anymore, just the static export. The Go API + Postgres run on AWS, provisioned via Terraform in `infra/terraform/` — see `infra/terraform/README.md` for the current architecture (cost-minimized: one EC2 instance + RDS, no ALB/ECS/Aurora) and the two-phase apply workflow. iOS/Android are separate EAS builds pointed at the deployed `EXPO_PUBLIC_API_URL` (`https://api.beatboxd.com`).
