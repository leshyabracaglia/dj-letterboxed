# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

## Working directory

Claude Code is always launched from this repo's root, so the shell already starts there and every command can run from it. Never `cd` in shell commands — not into subfolders, the scratchpad, `/tmp`, or `node_modules`, and not back to the repo root either. Run everything with repo-relative paths (`npx tsc --noEmit`, `grep -r foo components/`), and point tools at a subfolder with their own flag instead of `cd`-ing into it: `go -C server …`, `make -C server …`, `npm --prefix <dir> …`. There's rarely a reason to touch anything outside the repo.

## What this is

Letterboxd for DJ sets, and a community-built database of the electronic music scene. Users log a night out (event, venue, date, day/night, lineup), rate and review the night and optionally each DJ, tag the crowd and their friends, and follow each other for a feed with likes, comments and push notifications. Those reviews are also the database: every DJ, venue and event gets a page that collects its reviews, ratings and stats (who people saw where, how it rated). There's no editorial layer — all of it comes from what users log, so features that improve logging quality (deduping DJs/venues/events, Google Places venues, Spotify DJs) matter for the data, not just the UX.

Stack: Expo (React Native + React Native Web) with Expo Router, NativeWind for styling; a Go HTTP API deployed on AWS (ECS Fargate previously, currently a single EC2 instance running Docker Compose for cost reasons — see `infra/terraform/README.md`); AWS RDS Postgres; Clerk for auth. The web export still deploys via Vercel (static hosting only — the API used to live there too as tRPC Edge Functions, but moved off after an unfixable Vercel Edge Function bundler bug; see git history around the "move to aws and go backend" commit for the full story).

## Commands

Setup:
```
npm install
cp .env.example .env   # fill in EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY, EXPO_PUBLIC_API_URL
cp server/.env.example server/.env   # fill in DATABASE_URL, CLERK_*, SPOTIFY_*, GOOGLE_PLACES_API_KEY and EXPO_ACCESS_TOKEN (both optional) — see server/.env.example
```

Running locally — the app talks to the API over HTTP, so both need to be up:
```
npm run dev             # macOS: scripts/dev-windows.sh — docker compose up -d, migrate, seed, then opens dev:app and the API logs in separate Terminal.app windows
npm run dev:concurrent  # runs dev:api and dev:app together in one terminal via concurrently
npm run dev:api         # docker compose up for server/ (Postgres + Go API), API on :8080
npm run dev:app         # expo start — press w for web, i for iOS simulator
```

First-time local DB setup (against the docker-compose Postgres, entirely separate from the production RDS instance):
```
npm run db:migrate   # applies server/migrations/*.sql via golang-migrate
npm run db:seed      # fixture data (4 users, ~17 DJs, nights with/without an event name and with no/one/several DJs, none/some/every DJ rated, an unrated pre-night-rating night, another city, tags/likes/comments/favorites)
npm run db:reset     # migrate down, up, and re-seed
```

Inspecting production data (read-only, as the `beatboxd_readonly` role over SSM — see `infra/terraform/README.md`):
```
npm run db:prod      # read-only tunnel to production Postgres, opened in TablePlus/Postico (see infra/terraform/README.md)
npm run db:prod:query -- "SELECT …"   # one read-only query against production
```

Type checking: `npx tsc --noEmit` (client). Server: `go -C server build ./... && go -C server vet ./... && go -C server test ./...` (there is no lint script or unit test runner configured for the client).

End-to-end: `npm run test:e2e` (Playwright, `e2e/`, desktop + phone viewports of the web build, signed out). It starts its own API on :8090 against a fresh `beatboxd_e2e` database in the compose Postgres (recreated, migrated and seeded each run by `scripts/e2e-api.sh` — your dev `beatboxd` DB is untouched) and its own Metro on :8091 (`EXPO_PUBLIC_DEV_API_PORT` points the dev client at the e2e API). Needs Docker and Go; first time, `npx playwright install chromium`. Tests assert on seed fixtures, so keep `server/cmd/seed/main.go` and the specs in sync.

## Architecture

**Routing**: `app/` is Expo Router file-based routing. `(auth)` and `(tabs)` are route groups; `app/_layout.tsx` is the root layout and wraps everything in `ClerkProvider` → `QueryClientProvider`. All in-app links and navigation must go through the `ROUTES` constant in `lib/routes.ts` — never hardcode a path string in `Link href`, `router.push`/`replace`, or `Redirect href`. Static routes are plain `Href` values (`ROUTES.FEED`, `ROUTES.SIGN_IN`); dynamic routes are functions that build the `Href` from an id/slug (`ROUTES.DJ(slug)`, `ROUTES.USER(username)`). When a new route is added under `app/`, add a corresponding entry to `ROUTES` in the same change.

**Components & page layout**: generic, domain-agnostic UI primitives (`Text`, `Card`, `Button`, `Avatar`, `RatingStamp`, `EmptyState`, `Page`, `PageHeader`, …) live in `components/ui/` and are imported from its barrel (`components/ui`). Components that know about reviews/DJs/users (`ReviewCard`, `StatsSummary`, `FavoritesShowcase`, …) stay in `components/` — but only once they're used from two or more files. A component used by a single file lives in that file as an unexported function (Expo Router turns every file under `app/` into a route, so a screen's helper components can't sit beside it as separate files); promote it to `components/` when a second consumer appears. When pulling in a [React Native Reusables](https://reactnativereusables.com) component, adapt it straight into a single `components/ui/` file built on its `@rn-primitives/*` package with the app's API and theme (as `ui/Avatar` does) — don't keep a separate raw copy plus a wrapper. If a component needs RNR's `cn` helper, use `tailwind-merge` v2 (v3 requires Tailwind 4). Every screen renders inside `<Page>` (safe area + the concrete-wall background, optional `title`/`channel`/`header`, `fullBleed` for a hero that runs under the status bar), and lists/scroll views take `usePageContentStyle()` as their `contentContainerStyle` so content lines up with the shared horizontal gutter (`components/ui/layout.ts`) — don't hand-roll `SafeAreaView` or `padding: 16` on a screen. Custom top-of-screen blocks (profile/detail headers) go in `<PageHeader>` (with `border="primary" | "accent"` for the divider) to stay on the same gutter. The look is a dark-only "zine" (the app forces the dark color scheme in `app/_layout.tsx`): colored paper `Card`s (`tint` purple/red/near-black panel, optional `tilt`/`torn`), `RatingStamp` seals instead of stars for showing ratings, `Chip` tags, and Jersey 10 uppercase for headings and labels.

**API**: the Go service in `server/` (see `server/README` references in `infra/terraform/README.md` for deploy details). Handlers live in `server/internal/httpapi/`, one file per domain (`djs`, `events`, `venues`, `tags`, `follows`, `reviews` (logging a night in one shot, plus likes/comments), `favorites`, `users`, `moderation` (blocks and reports), `notifications` (the in-app list), `check_ins` (checking in at a venue to verify a review), `feed`, `push_tokens`, `app_version`, `ra` (Resident Advisor listings for the log screen's search, and matching an RA night's lineup/venue to DJs/Spotify and venues/Google Places), plus `webhooks` for the Clerk sync endpoint), wired up in `server/internal/httpapi/router.go`. Business logic that doesn't belong in a handler (the feed cursor, tag normalization, Spotify, Google Places, Resident Advisor and Expo push clients, slugify) lives in `server/internal/domain/`; DB access is hand-written SQL in `server/internal/db/queries/` against `pgx`/`pgxpool` (no ORM). This is a plain REST API (no tRPC), but it's not undocumented either: every handler carries `swag`-style `@Summary`/`@Param`/`@Success`/`@Router` doc comments, and `server/docs/{swagger.json,swagger.yaml}` (generated, not hand-written — run `make -C server openapi` after touching a handler's signature or docs) is served live at `/docs/*`. Response types on the client are generated from that spec too — see "Client data fetching" below — so a handler's real output shape and the client's compile-time types can't silently drift the way they could with plain hand-written types.

**Auth flow** (`server/internal/httpapi/middleware.go` + `server/internal/auth/clerk.go`): the client attaches a Clerk-issued bearer JWT on every request (`lib/api/client.ts`'s `useApi()`, via `getToken()` from `@clerk/expo`). The Go service verifies that JWT itself against Clerk's public JWKS (no Clerk SDK needed for this). `RequireAuth` then resolves the verified Clerk ID to a row in the local `users` table — and **lazily creates one with a fallback username if it doesn't exist yet**, in case the Clerk webhook hasn't landed. The webhook handler (`server/internal/httpapi/webhooks_handlers.go`, svix-verified) is the primary sync path for `user.created`/`user.updated`/`user.deleted`; the lazy-create in `RequireAuth` is just a race-condition fallback, not the main path — don't remove one without considering the other. On the client, `AuthProvider` (`lib/auth.tsx`, mounted in `app/_layout.tsx`) owns the single `/users/me` query; read the current user anywhere with `useCurrentUser()` (`{ me, isSignedIn, isLoaded, isLoadingMe }`) instead of writing another `useQuery` for it. After a profile update, `setQueryData(queryKeys.users.me(), updated)` still works — it updates the provider's query. Sign out with `useSignOut()` from `lib/push.ts`, never Clerk's `useAuth().signOut` directly: it unregisters the device's push token first, so the old account's notifications stop arriving on that device.

**Data model** (`server/migrations/*.sql`, plain Postgres DDL applied via `golang-migrate`): `users`, `djs`, `venues`, `events`, `reviews`, `review_lineup`, `review_likes`, `review_comments`, `review_tags`, `tags`, `review_tag_links`, `favorite_reviews`, `follows`, `push_tokens`, `blocks`, `reports`, `notifications`, `check_ins`. An `events` row is just a named party ("Innervisions NY", unique by `lower(name)` and `slug`) — not a night: it happens at any number of venues and dates and collects every review of it, and its page (`/event/<slug>`) rolls them up. `reviews` is the core entity: one person's night out, and the post. It has an optional `event_id` (null = a one-off night with no event name, just the venue), the venue (`venue_id`, with `venue` keeping the display name denormalized), `seen_at` (the day), `is_day`/`is_night` (when *this person* went — at least one set, both = day into night), and their `rating` and `review_text` of the night as a whole; `rating` is whole stars, an integer 1–5 (no half stars), null only on nights logged before nights were rated (migration 0021). The DJs they saw are its lineup in `review_lineup`, each with an optional `rating`/`review_text` of its own: a rated lineup row *is* a DJ review (there's no separate DJ review table or id). Likes, comments, tagged friends, descriptive tags, favorites, notifications and reports all hang off the review. Day/night and date live on the review, never the event: people at the same event can go during the day or at night, or on different dates, and there are no shared per-night records to merge them into. `POST /api/reviews` is the only way to create one: it takes `eventId` (picked from `GET /api/events?q=`) or `eventName` (found or created by name), the venue, date and day/night, the night's rating and text, the lineup with any DJ ratings, tags and tagged friends, and saves them in one transaction. A review is fixed once logged: `PATCH /api/reviews/{id}` only changes who was tagged as being there, and `DELETE /api/reviews/{id}` removes the night with everything on it. ("Log" survives only as the verb in the UI — "Log a night", the log tab.) The log tab opens on a search over Resident Advisor nights near the user (`/api/ra/*`, RA's unofficial GraphQL endpoint, cached in-process); picking one prefills the poster form via `GET /api/ra/events/{id}/match`. The area comes from the device's location each time the tab is opened (`lib/location.ts` geocodes the city on device; `lib/location.web.ts` sends coordinates and the server geocodes them with the Google Geocoding API, same key as Places), then the city of the user's latest review, then a manual city picker. A review is *verified* (`verified` in its response, a mark on its card) when its person checked in at its venue that night: `POST /api/check-ins` takes a precise fix (read only when they tap Check in on the log tab), measures it against the venue's coordinates (so only venues with coordinates, i.e. Google Places ones, can be checked in at), and keeps only the venue, time and distance, never the coordinates. Verified is derived on read (`reviewVerifiedExpr` in `queries/reviews.go`: a check-in from the start of the logged day to 8am the next morning, `seen_at` being local noon), so it doesn't matter whether the check-in or the review comes first. Reviews point at a `venues` row via `venue_id`; a venue is either linked to a Google Places place (`google_place_id`, unique; looked up via `GET /api/venues/places-search` and saved on first use) or typed in by hand (unique by `lower(name)`). Two different "tag" concepts — don't mix them up: `tags` + `review_tag_links` are free-form descriptive tags on a review ("packed", "groovy"; a shared library with some `is_default` seeds, names normalized by `domain.NormalizeTag`), while `review_tags` tags *users* (friends you went with) on a review. `follows` has no surrogate key, just a composite PK on `(follower_id, following_id)`. `push_tokens` keys on the Expo push token itself, so a device that signs in to another account moves to it. `blocks` hides two users from each other both ways: every review and comment list drops the other's posts (`withoutHidden` in `moderation_handlers.go`, so a new endpoint that lists reviews or comments needs it too), blocking drops follows between them, and follow/like/comment between them 403s. `reports` (a review, comment or user, a reason, and a snapshot of the text) are emailed to `REPORTS_EMAIL` via Resend when configured; the App Store expects them acted on within 24 hours. Schema changes: hand-write a new numbered `.up.sql`/`.down.sql` pair in `server/migrations/` (there's no schema-diffing tool), and remember production needs the migration applied before or alongside the deploy that uses it.

**Client data fetching**: `lib/api/client.ts`'s `useApi()` hook returns a small `{get, post, patch, del}` client bound to the current Clerk token, pointed at `EXPO_PUBLIC_API_URL` in production builds; in `__DEV__` it instead auto-targets `:8080` on the host serving the Metro bundle (page hostname on web, `Constants.expoConfig.hostUri` on native), so LAN IP changes need no `.env` edit. Each screen calls it directly with `@tanstack/react-query`'s `useQuery`/`useMutation`/`useInfiniteQuery`, using the key factories in `lib/api/queryKeys.ts` (no tRPC — keys are hand-assigned, not auto-derived). A query or mutation used by two or more screens gets a shared hook in `lib/api/hooks.ts` (e.g. `useUserReviews`, `useDjSearch`; current-user reads/writes live in `lib/auth.tsx` as `useCurrentUser`/`useUpdateProfile`) so the key, params and cache writes stay consistent; single-screen queries stay inline in that screen. Response types in `lib/api/types.ts` are aliased from `lib/api/generated.ts`, which is **generated, not hand-written** — `npm run codegen:api-types` regenerates `server/docs/swagger.json` from the Go handlers' doc comments (via `swag`) and then `lib/api/generated.ts` from that spec (via `swagger2openapi` + `openapi-typescript`; see `scripts/generate-api-types.sh`). Request body types in `lib/api/types.ts` stay hand-written (lower drift risk, and OpenAPI's json-schema shapes don't cleanly express TS's optional-vs-omitted distinction that `taggedUserIds` relies on). `.github/workflows/server-ci.yml` regenerates both the spec and the TS types on every PR touching `server/**` or `lib/api/**` and fails the build if either drifted from what's committed — so run `npm run codegen:api-types` and commit the result whenever a handler's shape changes. Nullable response fields: `swag` can't tell from a Go pointer that a field is "always present, sometimes null", so every response field that can be `null` (a pointer without `omitempty`) carries the struct tag `extensions:"x-nullable"` — that's what makes it `T | null` in the generated types. Add the tag to any new nullable response field, rather than patching the type by hand in `lib/api/types.ts`. Dates arrive as RFC3339 strings, not `Date` objects (screens already wrap them in `new Date(...)` where displayed).

**Notifications**: follows, new likes and comments on someone's review, and being tagged in someone else's night (on `POST /api/reviews` and `PATCH /api/reviews/{id}`) are recorded in `notifications` for the in-app list (`GET /api/notifications`, the bell in the feed header / web navbar, `app/notifications.tsx`; unread = newer than `users.notifications_seen_at`, reset by `POST /api/notifications/seen`) and trigger an Expo push (`server/internal/httpapi/notify.go`). Only a newly recorded notification pushes: partial unique indexes make repeat follows/likes/tags no-ops. A tag notification (and the tagged review's page, via `viewerLoggedNight`) offers to log the night yourself if you haven't, opening the log tab prefilled via `ROUTES.REVIEW_FROM(reviewId)`. They're sent in a goroutine after the request's own work succeeds, on a fresh context, and failures are only logged — never fail the triggering request on them. `queries.Follow`/`LikeReview` report whether a row was actually inserted so repeat follow/like toggles don't re-notify, and self-likes/comments are skipped. Tokens Expo reports as `DeviceNotRegistered` are deleted. The payload's `data` says what happened (`{type: "follow", username}` / `{type: "like" | "comment" | "tag", reviewId}`), never a path; the client maps it to `ROUTES` in `lib/push.ts`, which also registers the device (asking permission on first signed-in launch) and handles taps, including the one that cold-starts the app. `lib/push.web.ts` is a no-op stub (no web push). Separately, a re-engagement push (`server/internal/httpapi/reengage.go`, a ticker started from `cmd/api/main.go`) tells someone who hasn't made a signed-in request in 48h (`users.last_active_at`, written at most every 5 minutes by the auth middleware) that people they follow logged nights, at most once per 48h (`users.reengaged_at`); it isn't recorded in `notifications`, and its `{type: "following_logs"}` tap opens the feed. Push needs a dev/production build on a real device (not Expo Go on Android, not simulators) and APNs/FCM credentials in EAS; `EXPO_ACCESS_TOKEN` is only needed if the Expo project has enhanced push security on.

**Deployment**: Vercel builds the Expo web export (`expo export -p web`, see `vercel.json`) into `dist/` — no `/api/*` on Vercel anymore, just the static export. The Go API + Postgres run on AWS, provisioned via Terraform in `infra/terraform/` — see `infra/terraform/README.md` for the current architecture (cost-minimized: one EC2 instance + RDS, no ALB/ECS/Aurora) and the two-phase apply workflow. iOS/Android are separate EAS builds pointed at the deployed `EXPO_PUBLIC_API_URL` (`https://api.beatboxd.com`).
