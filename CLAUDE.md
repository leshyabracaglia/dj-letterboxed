# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

## Working directory

Claude Code is always launched from this repo's root, so the shell already starts there and every command can run from it. Never `cd` in shell commands — not into subfolders, the scratchpad, `/tmp`, or `node_modules`, and not back to the repo root either. Run everything with repo-relative paths (`npx tsc --noEmit`, `grep -r foo components/`), and point tools at a subfolder with their own flag instead of `cd`-ing into it: `go -C server …`, `make -C server …`, `npm --prefix <dir> …`. There's rarely a reason to touch anything outside the repo.

## What this is

Letterboxd for DJ sets, and a community-built database of the electronic music scene. Users log a night out (event, venue, date, day/night, lineup), write about the night and optionally each set, highlight the tracks that stood out (or post an unidentified ID for others to name), tag the crowd and their friends, and follow each other for a feed with likes, comments and push notifications. There are no star ratings, deliberately: the app is about positive, thoughtful discussion of sets, not scoring DJs (rating people you might meet is what sank SeenLive), so don't add a rating or ranking of DJs back in. Those reviews are also the database: every DJ, venue and event gets a page that collects its reviews, tracks and stats (who people saw where, what they played, how people describe them). There's no editorial layer — all of it comes from what users log, so features that improve logging quality (deduping DJs/venues/events, Google Places venues, Spotify DJs) matter for the data, not just the UX.

Stack: Expo (React Native + React Native Web) with Expo Router, NativeWind for styling; a Go HTTP API deployed on AWS (ECS Fargate previously, currently a single EC2 instance running Docker Compose for cost reasons — see `infra/terraform/README.md`); AWS RDS Postgres; Clerk for auth. The web export still deploys via Vercel (static hosting only — the API used to live there too as tRPC Edge Functions, but moved off after an unfixable Vercel Edge Function bundler bug; see git history around the "move to aws and go backend" commit for the full story).

## Commands

Setup:
```
npm install
cp .env.example .env   # fill in EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY, EXPO_PUBLIC_API_URL
cp server/.env.example server/.env   # fill in DATABASE_URL, CLERK_*, SPOTIFY_*, GOOGLE_PLACES_API_KEY and EXPO_ACCESS_TOKEN (both optional) — see server/.env.example
```

Running locally — the app talks to the API over HTTP, so both need to be up:
```
npm run dev             # macOS: scripts/dev-windows.sh — docker compose up -d, migrate, seed, then opens dev:app and the API logs in separate Terminal.app windows
npm run dev:concurrent  # runs dev:api and dev:app together in one terminal via concurrently
npm run dev:api         # docker compose up for server/ (Postgres + Go API), API on :8080
npm run dev:app         # expo start — press w for web, i for iOS simulator
```

First-time local DB setup (against the docker-compose Postgres, entirely separate from the production RDS instance):
```
npm run db:migrate   # applies server/migrations/*.sql via golang-migrate
npm run db:seed      # fixture data (6 users, ~17 DJs, nights with/without an event name and with no/one/several DJs, none/some/every set written about, tracks of every source incl. typed-in and unidentified IDs (open with suggestions and a clip, open with nothing, and accepted), lists, favorite venues, check-ins incl. two friends at the same club the same night, another city, tags/likes/comments/favorites, a blocked and reported user, an empty profile, every notification type read and unread). Set `SEED_CLERK_ID` (and optionally `SEED_USERNAME`) in `server/.env` to your own Clerk user id and the seed builds your account into all of it too (`seedYou`: verified and unverified nights, IDs with suggestions and a clip, friends, a tag on a night you haven't logged, a list, a block, the What's new sheet unseen), so signing in locally shows everything filled in
npm run db:reset     # migrate down, up, and re-seed
```

Inspecting production data (read-only, as the `beatboxd_readonly` role over SSM — see `infra/terraform/README.md`):
```
npm run db:prod      # read-only tunnel to production Postgres, opened in TablePlus/Postico (see infra/terraform/README.md)
npm run db:prod:query -- "SELECT …"   # one read-only query against production
```

Client checks: `npx tsc --noEmit`, `npm run lint` (ESLint via `expo lint`, `eslint.config.js`), `npm run format:check` (Prettier; `npm run format` to fix) and `npm test` (Jest with `jest-expo`). Server: `go -C server build ./... && go -C server vet ./... && go -C server test ./...`.

Client unit tests sit next to the code they test as `*.test.ts` (never under `app/`, where every file is a route), with shared API-object builders in `test/fixtures.ts`. They cover the pure logic: `lib/format`, `lib/review`, the log form's reducer and draft checks, the review cache helpers. Screens are covered end to end instead.

End-to-end: `npm run test:e2e` (Playwright, `e2e/`, desktop + phone viewports of the web build, signed out). It starts its own API on :8090 against a fresh `beatboxd_e2e` database in the compose Postgres (recreated, migrated and seeded each run by `scripts/e2e-api.sh` — your dev `beatboxd` DB is untouched) and its own Metro on :8091 (`EXPO_PUBLIC_DEV_API_PORT` points the dev client at the e2e API). Needs Docker and Go; first time, `npx playwright install chromium`. Tests assert on seed fixtures, so keep `server/cmd/seed/main.go` and the specs in sync.

## Architecture

**Routing**: `app/` is Expo Router file-based routing. `(auth)` and `(tabs)` are route groups; `app/_layout.tsx` is the root layout and wraps everything in `ClerkProvider` → `QueryClientProvider`. All in-app links and navigation must go through the `ROUTES` constant in `lib/routes.ts` — never hardcode a path string in `Link href`, `router.push`/`replace`, or `Redirect href`. Static routes are plain `Href` values (`ROUTES.FEED`, `ROUTES.SIGN_IN`); dynamic routes are functions that build the `Href` from an id/slug (`ROUTES.DJ(slug)`, `ROUTES.USER(username)`). When a new route is added under `app/`, add a corresponding entry to `ROUTES` in the same change.

**Components & page layout**: generic, domain-agnostic UI primitives (`Text`, `Card`, `Button`, `Avatar`, `Stamp`, `EmptyState`, `Page`, `PageHeader`, …) live in `components/ui/` and are imported from its barrel (`components/ui`). Components that know about reviews/DJs/users (`ReviewCard`, `StatsSummary`, `FavoritesShowcase`, …) stay in `components/` — but only once they're used from two or more files. A component used by a single file lives in that file as an unexported function (Expo Router turns every file under `app/` into a route, so a screen's helper components can't sit beside it as separate files, and a route file exports nothing but its screen); promote it to `components/` when a second consumer appears. The exception is a screen big enough to have parts of its own: those go in a feature folder, `components/<feature>/` (`components/log/` for the log tab, `components/review/` for a review's page), so the route file stays a thin screen. Import across folders through the `@/` alias, never `../` (lint enforces it). Color values come from `lib/colors.js`, the single palette Tailwind builds its classes from: use the classes in `className`, and import `colors` only where a raw value is needed (SVG fills, `ActivityIndicator`, navigator options), never a hex literal. Display type (Jersey 10, uppercase) is `<Text variant="display">`, with size and color in `className`. Icons are always `Icon` from `components/ui` (lint blocks raw `@expo/vector-icons`). Platform checks use `isWeb`/`isIos`/`isAndroid` from `lib/platform.ts`; system alerts and confirms use `showAlert`/`confirmDestructive` from `lib/dialog.ts` (React Native Web's `Alert.alert` does nothing); a Clerk error's user-facing text comes from `clerkErrorMessage` in `lib/clerk.ts`. When pulling in a [React Native Reusables](https://reactnativereusables.com) component, adapt it straight into a single `components/ui/` file built on its `@rn-primitives/*` package with the app's API and theme (as `ui/Avatar` does) — don't keep a separate raw copy plus a wrapper. If a component needs RNR's `cn` helper, use `tailwind-merge` v2 (v3 requires Tailwind 4). Every screen renders inside `<Page>` (safe area + the concrete-wall background, optional `title`/`channel`/`header`, `fullBleed` for a hero that runs under the status bar), and lists/scroll views take `usePageContentStyle()` as their `contentContainerStyle` so content lines up with the shared horizontal gutter (`components/ui/layout.ts`) — don't hand-roll `SafeAreaView` or `padding: 16` on a screen. Custom top-of-screen blocks (profile/detail headers) go in `<PageHeader>` (with `border="primary" | "accent"` for the divider) to stay on the same gutter. The look is a dark-only "zine" (the app forces the dark color scheme in `app/_layout.tsx`): colored paper `Card`s (`tint` purple/red/near-black panel, optional `tilt`/`torn`), `Stamp` seals (a dated passport stamp on every night via `NightStamp`, counts on DJ/event pages, the profile passport and favorite clubs, "ID'D" on tracks someone named), `Chip` tags, and Jersey 10 uppercase for headings and labels.

**API**: the Go service in `server/` (see `server/README` references in `infra/terraform/README.md` for deploy details). Handlers live in `server/internal/httpapi/`, one file per domain (`djs`, `events`, `venues`, `tags`, `follows`, `reviews` (logging a night in one shot, plus likes/comments), `tracks` (Spotify track search, reading a pasted track link, and ID requests: suggesting and accepting what an unidentified track is), `lists`, `favorites` (favorite reviews and venues), `users`, `moderation` (blocks and reports), `notifications` (the in-app list), `check_ins` (checking in at a venue to verify a review), `feed`, `push_tokens`, `app_version`, `ra` (Resident Advisor listings for the log screen's search, and matching an RA night's lineup/venue to DJs/Spotify and venues/Google Places), plus `webhooks` for the Clerk sync endpoint), wired up in `server/internal/httpapi/router.go`. Rate limits (`ratelimit.go`, `go-chi/httprate`, in memory) are set in the router: every request per client IP (the rightmost `X-Forwarded-For`, set by Caddy — never chi's `RealIP`, which trusts headers clients can spoof), every signed-in write per user, and tighter per-user limits on endpoints that are billed (Google Places) or create shared records (reviews, DJs, comments, reports, check-ins, lists, ID suggestions) — give a new endpoint of that kind its own `limitByUser`. Per-user limits can be multiplied by signing up more accounts, so every Google call (Places and Geocoding, from any user) also counts against one app-wide daily budget inside `domain.PlacesClient` (`GOOGLE_PLACES_DAILY_LIMIT`, default 2000); past it the client returns `ErrPlacesOverBudget` and handlers degrade as if Places weren't configured (check `domain.PlacesUnavailable(err)`). Repeat lookups (reverse geocoding, an RA venue's match) are cached there for a day. Request bodies are capped at 1MB, and the request log leaves out query strings (they carry coordinates and searches). Business logic that doesn't belong in a handler (the feed cursor, tag normalization, Spotify, track links (`TrackClient`: reads a pasted Spotify/SoundCloud/Apple Music/Shazam link through each service's own fixed lookup endpoint — never fetches the pasted URL — and caches it), Google Places, Resident Advisor and Expo push clients, slugify) lives in `server/internal/domain/`; DB access is hand-written SQL in `server/internal/db/queries/` against `pgx`/`pgxpool` (no ORM). This is a plain REST API (no tRPC), but it's not undocumented either: every handler carries `swag`-style `@Summary`/`@Param`/`@Success`/`@Router` doc comments, and `server/docs/{swagger.json,swagger.yaml}` (generated, not hand-written — run `make -C server openapi` after touching a handler's signature or docs) is served live at `/docs/*`. Response types on the client are generated from that spec too — see "Client data fetching" below — so a handler's real output shape and the client's compile-time types can't silently drift the way they could with plain hand-written types.

**Auth flow** (`server/internal/httpapi/middleware.go` + `server/internal/auth/clerk.go`): the client attaches a Clerk-issued bearer JWT on every request (`lib/api/client.ts`'s `useApi()`, via `getToken()` from `@clerk/expo`). The Go service verifies that JWT itself against Clerk's public JWKS (no Clerk SDK needed for this). `RequireAuth` then resolves the verified Clerk ID to a row in the local `users` table — and **lazily creates one with a fallback username if it doesn't exist yet**, in case the Clerk webhook hasn't landed. The webhook handler (`server/internal/httpapi/webhooks_handlers.go`, svix-verified) is the primary sync path for `user.created`/`user.updated`/`user.deleted`; the lazy-create in `RequireAuth` is just a race-condition fallback, not the main path — don't remove one without considering the other. On the client, `AuthProvider` (`lib/auth.tsx`, mounted in `app/_layout.tsx`) owns the single `/users/me` query; read the current user and whether anyone is signed in anywhere with `useCurrentUser()` (`{ me, isSignedIn, isLoaded, isLoadingMe }`) instead of writing another `useQuery` for it or calling Clerk's `useAuth()` (lint allows that only under `lib/`). After a profile update, `setQueryData(queryKeys.users.me(), updated)` still works — it updates the provider's query. Sign out with `useSignOut()` from `lib/push.ts`, never Clerk's `useAuth().signOut` directly: it unregisters the device's push token first, so the old account's notifications stop arriving on that device.

**Data model** (`server/migrations/*.sql`, plain Postgres DDL applied via `golang-migrate`): `users`, `djs`, `venues`, `events`, `reviews`, `review_lineup`, `review_likes`, `review_comments`, `review_tags`, `tags`, `review_tag_links`, `review_tracks`, `track_suggestions`, `track_clips`, `favorite_reviews`, `favorite_venues`, `lists`, `list_items`, `follows`, `push_tokens`, `blocks`, `reports`, `notifications`, `check_ins`. An `events` row is just a named party ("Innervisions NY", unique by `lower(name)` and `slug`) — not a night: it happens at any number of venues and dates and collects every review of it, and its page (`/event/<slug>`) rolls them up. `reviews` is the core entity: one person's night out, and the post. It has an optional `event_id` (null = a one-off night with no event name, just the venue), the venue (`venue_id`, with `venue` keeping the display name denormalized), `seen_at` (the day), `is_day`/`is_night` (when *this person* went — at least one set, both = day into night), and their `review_text` of the night as a whole. (The `rating` columns on `reviews` and `review_lineup` are left over from when nights and sets were rated; nothing reads or writes them, and the API ignores a `rating` an older app build sends.) The DJs they saw are its lineup in `review_lineup`, each with an optional `review_text` of its own: a lineup row with text, or with tracks from that DJ, *is* a DJ review (there's no separate DJ review table or id; `reviewedSets`/`soloSet` in `lib/review.ts`). `review_tracks` are the tracks they highlighted (at most 10): each from a lineup DJ (`dj_id`, a composite FK onto `review_lineup`) or the night as a whole (null), with a note; from a music service (`source` + `external_id`, its link and cover art — artwork only from those services' CDNs, `domain.IsTrackArtworkURL`) or typed in (`source = 'manual'`); one with no title is an unidentified ID. Anyone not blocked by the poster can suggest what an ID is (`track_suggestions`, `POST /api/tracks/{id}/suggestions`); the poster accepts one (`POST /api/track-suggestions/{id}/accept`), which fills in the track and credits the suggester (`identified_by_user_id`), and the poster naming their own ID skips the suggestion step. The poster can attach a recording to an ID (`track_clips`: at most 15 seconds of AAC/M4A, kept in Postgres as `bytea` since clips are tiny; recorded in the native app with `expo-audio`, never on web, whose recordings iPhones can't play). It's uploaded raw (`PUT /api/tracks/{id}/clip`, `useUploadTrackClip`, the one call outside openapi-fetch), streamed inline with Range support by `GET /api/tracks/{id}/clip` and never offered as a download, deleted when the ID is accepted (not on a timer), and reportable (`trackId` in `POST /api/reports`); the privacy policy and terms describe this, so keep them in step with any change. DJ pages roll tracks up as "Tracks people loved" (`GetDjTopTracks`: identified tracks, the same title and artist counted once across services) and a portrait (`GetDjPortrait`: the most-liked set review as a pull quote, where they're seen most, the tags on their nights). Likes, comments, tagged friends, descriptive tags, tracks, favorites, list items, notifications and reports all hang off the review. Day/night and date live on the review, never the event: people at the same event can go during the day or at night, or on different dates, and there are no shared per-night records to merge them into. `POST /api/reviews` is the only way to create one: it takes `eventId` (picked from `GET /api/events?q=`) or `eventName` (found or created by name), the venue, date and day/night, the night's text, the lineup with anything said about each set, the tracks, tags and tagged friends, and saves them in one transaction. A review is fixed once logged: `PATCH /api/reviews/{id}` only changes who was tagged as being there, and `DELETE /api/reviews/{id}` removes the night with everything on it. ("Log" survives only as the verb in the UI — "Log a night", the log tab.) The log tab opens on a search over Resident Advisor nights near the user (`/api/ra/*`, RA's unofficial GraphQL endpoint, cached in-process); picking one prefills the poster form via `GET /api/ra/events/{id}/match`. The area comes from the device's location each time the tab is opened (`lib/location.ts` geocodes the city on device; `lib/location.web.ts` sends coordinates and the server geocodes them with the Google Geocoding API, same key as Places), then the city of the user's latest review, then a manual city picker. A review is *verified* (`verified` in its response, a mark on its card) when its person checked in at its venue that night: Tapping Check in on the log tab reads a precise fix and lists up to 5 clubs/bars within 400m (`GET /api/check-ins/nearby`: saved venues with coordinates plus a Google Places Nearby Search, a saved place listed once); they pick the one they're at, and `POST /api/check-ins` (a `venueId`, or a `placeId` that's saved as a venue only once the check-in passes, so a review picking the same Google place lands on the same venue) measures the fix against the venue's coordinates (so only venues with coordinates, i.e. Google Places ones, can be checked in at), and keeps only the venue, time and distance, never the coordinates. Verified is derived on read (`reviewVerifiedExpr` in `queries/reviews.go`: a check-in from the start of the logged day to 8am the next morning, `seen_at` being local noon), so it doesn't matter whether the check-in or the review comes first. A user's passport (in `GET /api/users/{username}/stats`) is every venue they've logged a night at or checked in at; they can pin up to three of those as favorite venues (`favorite_venues`, `PATCH /api/users/me/favorite-venues`). Two separate "who was there" ideas — don't mix them up: tagging friends on a review (`review_tags`, chosen by the poster) is one; the other is discovery from check-ins only. When someone checks in and a friend (two users who follow each other, `mutualFollowCond` in `queries/friends.go`) checked in at the same venue in the last 12 hours, `POST /api/check-ins` returns them as `friendsHere` and both people get a `here_too` notification about the other. `lists` are curated by anyone: `list_items` are anyone's nights, or one DJ's set on a night (`dj_id`, FK onto `review_lineup`), each with a note. Reviews point at a `venues` row via `venue_id`; a venue is either linked to a Google Places place (`google_place_id`, unique; looked up via `GET /api/venues/places-search` and saved on first use) or typed in by hand (unique by `lower(name)`). Two different "tag" concepts — don't mix them up: `tags` + `review_tag_links` are free-form descriptive tags on a review ("packed", "groovy"; a shared library with some `is_default` seeds, names normalized by `domain.NormalizeTag`), while `review_tags` tags *users* (friends you went with) on a review. `follows` has no surrogate key, just a composite PK on `(follower_id, following_id)`. `push_tokens` keys on the Expo push token itself, so a device that signs in to another account moves to it. `blocks` hides two users from each other both ways: every review and comment list drops the other's posts (`withoutHidden` in `moderation_handlers.go`, so a new endpoint that lists reviews or comments needs it too), blocking drops follows between them, and follow/like/comment between them 403s. Every endpoint that saves user-written text (reviews, DJ review text, tracks and their notes, ID suggestions, list titles/descriptions/notes, event/venue names, tags, comments, profiles, DJs, Clerk-synced names) runs it through the content filter `domain.IsObjectionable` (slurs, hate, sexual content involving minors, "kill yourself" abuse; ordinary swearing is allowed) and 400s with `domain.ErrObjectionable` — a new text field needs it too. `reports` (a review, comment or user, a reason, and a snapshot of the text and the reported username, so a report outlives the reported account: `reported_user_id` goes null when it's deleted) are emailed to `REPORTS_EMAIL` via Resend when configured; the App Store expects them acted on within 24 hours. Schema changes: hand-write a new numbered `.up.sql`/`.down.sql` pair in `server/migrations/` (there's no schema-diffing tool), and remember production needs the migration applied before or alongside the deploy that uses it.

**Client data fetching**: `lib/api/client.ts`'s `useApi()` hook returns an [`openapi-fetch`](https://openapi-ts.dev/openapi-fetch/) client typed from the generated spec and bound to the current Clerk token, pointed at `EXPO_PUBLIC_API_URL` in production builds; in `__DEV__` it instead auto-targets `:8080` on the host serving the Metro bundle (page hostname on web, `Constants.expoConfig.hostUri` on native), so LAN IP changes need no `.env` edit. Calls name the spec's path, with path/query params under `params` and the request body under `body`, and are wrapped in `unwrap()`, which returns the typed data or throws an `ApiError` (status plus the server's error code and message): `unwrap(api.GET("/api/djs/{slug}", { params: { path: { slug } } }))`. So a wrong path, param or body, or a response read as the wrong type, fails to compile; never re-type a response with a generic or a cast. A query that waits on a value (a route param, the loaded profile) passes `skipToken` as its `queryFn` until it has one, rather than `enabled: !!x` plus a `!`. Each screen calls it directly with `@tanstack/react-query`'s `useQuery`/`useMutation`/`useInfiniteQuery`, using the key factories in `lib/api/queryKeys.ts` (no tRPC — keys are hand-assigned, not auto-derived). A query or mutation used by two or more screens gets a shared hook in `lib/api/hooks.ts` (e.g. `useUserReviews`, `useDjSearch`; current-user reads/writes live in `lib/auth.tsx` as `useCurrentUser`/`useUpdateProfile`) so the key, params and cache writes stay consistent; single-screen queries stay inline in that screen. A change to one review that every list showing it should reflect (a like, a comment count, tagged friends) goes through `patchCachedReview` in `lib/api/cache.ts` rather than refetching each list; `findCachedReview` there opens a review's page instantly from a list's copy, and `REVIEW_LIST_PREFIXES` names every query that can hold a review, so a new list query that shows reviews needs its prefix added there. Response types in `lib/api/types.ts` are aliased from `lib/api/generated.ts`, which is **generated, not hand-written** — `npm run codegen:api-types` regenerates `server/docs/swagger.json` from the Go handlers' doc comments (via `swag`) and then `lib/api/generated.ts` from that spec (via `swagger2openapi` + `openapi-typescript`; see `scripts/generate-api-types.sh`). Request body types come from the spec too: `swag` runs with `--requiredByDefault`, so mark a request struct's optional fields `json:"…,omitempty"` (it has no effect on decoding) or the generated type will demand them. The only hand-written ones in `lib/api/types.ts` narrow a spec type where it can't say "exactly one of" (`CreateReportInput`, `CheckInInput`); they're still checked against the spec at each call. `.github/workflows/server-ci.yml` regenerates both the spec and the TS types on every PR touching `server/**` or `lib/api/**` and fails the build if either drifted from what's committed — so run `npm run codegen:api-types` and commit the result whenever a handler's shape changes. Nullable response fields: `swag` can't tell from a Go pointer that a field is "always present, sometimes null", so every response field that can be `null` (a pointer without `omitempty`) carries the struct tag `extensions:"x-nullable"` — that's what makes it `T | null` in the generated types. Add the tag to any new nullable response field, rather than patching the type by hand in `lib/api/types.ts`. Dates arrive as RFC3339 strings, not `Date` objects (screens already wrap them in `new Date(...)` where displayed).

**Notifications**: follows, new likes and comments on someone's review, being tagged in someone else's night (on `POST /api/reviews` and `PATCH /api/reviews/{id}`), someone suggesting what an ID on your night is (`id_suggested`) or accepting your suggestion (`id_accepted`), and a friend checking in at the same venue as you the same night (`here_too`, sent to both of you, about the venue via `notifications.venue_id` rather than a review; at most once per pair per venue per 12 hours) are recorded in `notifications` for the in-app list (`GET /api/notifications`, the bell in the feed header / web navbar, `app/notifications.tsx`; unread = newer than `users.notifications_seen_at`, reset by `POST /api/notifications/seen`) and trigger an Expo push (`server/internal/httpapi/notify.go`). Only a newly recorded notification pushes: partial unique indexes make repeat follows/likes/tags no-ops. A tag notification (and the tagged review's page, via `viewerLoggedNight`) offers to log the night yourself if you haven't, opening the log tab prefilled via `ROUTES.REVIEW_FROM(reviewId)`. They're sent in a goroutine after the request's own work succeeds, on a fresh context, and failures are only logged — never fail the triggering request on them. `queries.Follow`/`LikeReview` report whether a row was actually inserted so repeat follow/like toggles don't re-notify, and self-likes/comments are skipped. Tokens Expo reports as `DeviceNotRegistered` are deleted. The payload's `data` says what happened (`{type: "follow" | "here_too", username}` / `{type: "like" | "comment" | "tag" | "id_suggested" | "id_accepted", reviewId}`), never a path; the client maps it to `ROUTES` in `lib/push.ts`, which also registers the device (asking permission on first signed-in launch) and handles taps, including the one that cold-starts the app. `lib/push.web.ts` is a no-op stub (no web push). Separately, a re-engagement push (`server/internal/httpapi/reengage.go`, a ticker started from `cmd/api/main.go`) tells someone who hasn't made a signed-in request in 48h (`users.last_active_at`, written at most every 5 minutes by the auth middleware) that people they follow logged nights, at most once per 48h (`users.reengaged_at`); it isn't recorded in `notifications`, its `{type: "following_logs"}` tap opens the feed, and users can turn it off in Settings (`users.reengage_push`, via `GET`/`PATCH /api/users/me/settings` — the caller's own preferences, kept off `db.User` because that's public). Push needs a dev/production build on a real device (not Expo Go on Android, not simulators) and APNs/FCM credentials in EAS; `EXPO_ACCESS_TOKEN` is only needed if the Expo project has enhanced push security on.

**Deployment**: Vercel builds the Expo web export (`expo export -p web`, see `vercel.json`) into `dist/` — no `/api/*` on Vercel anymore, just the static export. The Go API + Postgres run on AWS, provisioned via Terraform in `infra/terraform/` — see `infra/terraform/README.md` for the current architecture (cost-minimized: one EC2 instance + RDS, no ALB/ECS/Aurora) and the two-phase apply workflow. iOS/Android are separate EAS builds pointed at the deployed `EXPO_PUBLIC_API_URL` (`https://api.beatboxd.com`).
